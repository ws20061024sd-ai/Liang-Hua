### B5. 数据库连接管理不规范——存在连接泄漏风险

**影响范围**：至少 15 处手动 `conn.close()`

**问题**：所有 SQLite 操作都是手动 `conn = connect()` + `conn.close()` 模式。如果在 `connect()` 和 `close()` 之间抛出异常，连接永远不会关闭。

**典型风险代码**：

```python
# downloader.py L208 — 如果在 UPDATE 和 conn.close() 之间异常，连接泄漏
conn = get_db_connection()
conn.execute("""UPDATE daily_kline SET pct_change = (...)""")
fixed = conn.total_changes
conn.commit()
conn.close()  # ← 如果上面任何一步抛异常，这行不执行
```

**修复**：全部改用 context manager：

```python
def fix_pct_change():
    with get_db_connection() as conn:
        conn.execute("""UPDATE daily_kline SET pct_change = (...)""")
        fixed = conn.total_changes
        conn.commit()
    # with 块结束时自动 close()，即使抛异常也会关闭
```

需要改造 `get_db_connection()` 以支持 context manager，或者直接用 `sqlite3.connect()` 本身就支持 context manager（Python 3.11+）。

### H1. 缺少日志系统——生产环境排查全靠 cron 重定向

**现状**：全部 27 个文件使用 `print()`，cron 任务的日志通过 `>> logs/cron.log 2>&1` 捕获。

**问题**：
- 日志无时间戳，无法构建事件时间线
- 无法按级别过滤（全部混在一起）
- 多模块并行时日志交错，难以追踪
- 磁盘日志无限增长（无 rotation）

**方案**：
```python
# config/logging_config.py（新增文件）
import logging
import sys
from logging.handlers import RotatingFileHandler

def setup_logging(name: str = "quant"):
    logger = logging.getLogger(name)
    logger.setLevel(logging.INFO)
    
    # 控制台 handler
    ch = logging.StreamHandler(sys.stdout)
    ch.setFormatter(logging.Formatter('%(asctime)s [%(levelname)s] %(name)s: %(message)s'))
    logger.addHandler(ch)
    
    # 文件 handler（自动 rotation，保留 7 天）
    fh = RotatingFileHandler('logs/quant.log', maxBytes=10*1024*1024, backupCount=7)
    fh.setFormatter(logging.Formatter('%(asctime)s [%(levelname)s] %(name)s: %(message)s'))
    logger.addHandler(fh)
    
    return logger
```

两个文件各约 180 和 225 行，其中 `send()` / `send_report()` 函数有 ~20 行几乎相同的 HTTP 请求逻辑。格式化函数 `format_signals()` 和 `format_report()` 也有很多相似的结构化 Markdown 生成。

**建议**：提取公共的 `_send_dingtalk(markdown, title)` 和 `_format_table()` 到共享模块。

### M7. 字符串魔数散落各处

`'BUY'`、`'SELL'`、`'passed'`、`'blocked'`、`'strong'`、`'shaky'`、`'weak'`、`'crash'` 等字符串在 10+ 个文件中重复出现。如果某天修改了某个状态字符串，需要全局搜索替换。

**建议**：在 `config/constants.py` 中定义枚举或常量：
```python
from enum import StrEnum
class Action(StrEnum):
    BUY = "BUY"
    SELL = "SELL"
```

### M8. sector_trend.py SQL 字符串拼接

**文件**：[analysis/sector_trend.py:87-88](analysis/sector_trend.py#L87-L88)

```python
"WHERE date IN ({})".format(','.join(f"'{d}'" for d in dates))
```

虽然 `dates` 来自同一 DB 查询（理论安全），但不符合 SQL 最佳实践。应使用参数化查询或至少用 `?` 占位符。

### M9. 缺少交易日历

`run.py` 和 `report.py` 只用 `datetime.now().weekday() >= 5` 判断周末，但无法处理：
- 春节、国庆等法定长假（7 天）
- 调休工作日（周六上班但股市不开盘，或反之）
- 半天交易日（如春节前最后一个交易日）

**方案**：使用 `akshare` 自带的交易日历，或引入 `pandas_market_calendars` / `chinese_calendar`。

### M10. 无健康检查端点

服务器上的定时任务只有 cron 重定向日志。如果：
- Python 进程崩溃
- 数据库损坏
- 磁盘满
- 网络断

没有任何主动告警机制。服务器上的 `cron.log` 只能被动查看。

**最低方案**：加第三条 cron `15 21 * * 1-5`，执行健康检查脚本：
```bash
# 检查今天 signal_history 是否有新记录，没有则发钉钉告警
```

### M11. 无数据库自动备份

`data/stocks.db` 是单点故障。SQLite 文件损坏 = 全部数据丢失。

**方案**：每日 cron 后自动备份，保留最近 7 天：
```bash
cp data/stocks.db data/backups/stocks_$(date +%Y%m%d).db
```

### M12. 汇率/退市/除权除息未处理

- 退市股票：成分股调整后退市股票数据不再更新，但历史数据仍在 DB 中
- 除权除息：目前的复权依赖 AKShare 的 `qfq`（前复权）参数，未做本地校验
- 分红：未考虑股息再投资的收益

### M13. local_factor_backtest.py 因子计算与 factor_engine.py 不一致

两个文件都实现了因子计算，但逻辑有差异：

| 差异点 | factor_engine.py | local_factor_backtest.py |
|--------|:--:|:--:|
| 动量计算 | 12月收益 - 1月收益 | 简单 12月收益 |
| 换手率因子 | 20日均换手率 | 20日/60日均量比 |
| 数据范围 | `<= date`（包含当日） | 截至上一交易日 |

这导致回测结果与实盘逻辑不一致。应该统一为同一套因子计算函数。

---

### M14. 因子引擎缺财务数据时权重未重新分配

**文件**：[engine/factor_engine.py:262-270](engine/factor_engine.py#L262-L270)

当 PE/PB/ROE 数据不可用时，代码将估值/质量权重设为 0，但**未将释放的权重重新分配给价格因子**。总权重 = 0.65，而非 1.0。

虽然相对排名不变（因为是线性变换），但：
- 绝对得分值偏低
- 如果未来加入阈值过滤（如"score > 0.5 才推荐"），会因总体偏低而误过滤

### M15. 无 CI/CD 管道

当前部署流程完全手动：`git push` → SSH 到服务器 → `git pull`。没有：
- 自动化测试
- 代码风格检查
- 部署前验证
- 部署失败回滚

对于单人项目，当前流程可以接受。但如果未来多人协作，必须引入 CI/CD。

## 九、总结

### 项目亮点
- 短短 1 个月从零搭建了一套完整的 A 股量化系统（数据→策略→风控→推送→回测）
- 架构设计合理，模块职责清晰

### 最大的三个风险
1. **无声的失败**：静默异常吞没是项目所有长期隐藏 Bug 的共同根因
2. **零测试**：5,115 行代码没有一行测试，任何修改都是盲飞
3. **安全裸奔**：Token 明文在 Git 中，数据库无备份

### 一句话建议
> 暂停新功能开发 1-2 周，集中偿还技术债（日志 + 测试 + 密钥轮换 + 异常处理规范），
> 让系统从"能跑"升级到"跑得让人放心"，再继续推进多因子策略。
