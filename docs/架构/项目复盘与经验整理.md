## ⚠️ 遇到问题时的自动化 Skill 操作流程

> 2026-06-18 确立——聚宽策略8次报错×2天浪费的根本教训。

**不要手动瞎改。不要凭猜测修。按以下流程自动执行：**

```
遇到任何问题（报错/异常/数据不对）
    │
    ▼
Step 1: 诊断
  /verify 或 debugging-and-error-recovery
  → 系统排查根因（不是猜，是逐层排除）
    │
    ▼
Step 2: 调研（如果涉及不熟悉的平台/API）
  /deep-research 或 WebSearch
  → 搜索官方文档 + 社区最佳实践 + 已知坑点
  → 输出 "XXX编码须知" 文档
    │
    ▼
Step 3: 验证假设
  写 ≤10 行最小验证脚本
  → 在目标环境实测，确认 API 行为的真相
  → 以实测为准（文档可能过时！）
    │
    ▼
Step 4: 制定方案
  spec-driven-development
  → 基于验证结果写数据流，标注每一步的类型转换
    │
    ▼
Step 5: 分步实现
  incremental-implementation
  → 每一步验证通过再走下一步
    │
    ▼
Step 6: 审查
  /code-review 或 code-review-and-quality
  → 对照审查规范逐项检查
```

**禁止的行为**：

- ❌ 报错 → 改一行 → 再跑 → 又报错 → 再改（"修一下再跑"循环）
- ❌ 凭记忆/经验假设 API 返回格式（"应该是宽表吧"）
- ❌ 不跑环境验证就写完整代码
- ❌ 2次以上同类报错还不质疑底层假设

**触发条件**：只要满足以下任一条件，立即启动上述流程：

- 同一个问题出现 2 次以上
- 涉及新平台/新 API
- 不确定数据格式
- 回测结果异常（收益0%或极高）

## 二、遇到的问题与解决方案（按发生顺序）

### 问题1：AKShare 东方财富 API 全部连不上

**现象**：首次 `run.py --init` 下载 300 只股票，全部失败。报 `ProxyError`。

**排查过程**：

```
1. 怀疑代理 → 检查系统代理（Clash on 127.0.0.1:7897）
2. 关代理 → 仍然失败，报 SSL 证书错误
3. 发现 Python 3.14 缺少根证书 → 运行 Install Certificates.command 修复
4. SSL 修复后 → 还是连不上，报 RemoteDisconnected
5. curl 测试 → 能用但 Python 不行 → 怀疑 TLS 或 IP 问题
6. 换数据源 → 新浪 source 能用 ✅
```

**根因**：多层叠加——代理拦截 + SSL 证书缺失 + 东方财富 API 不稳定。

**最终方案**：优先用新浪数据源（`stock_zh_a_daily`），东方财富作备用。新浪稳定且不需要额外配置。

**教训**：

- 数据源必须有备份，不能依赖单一 API
- 启动时清除代理环境变量
- 在 downloader.py 开头加 `os.environ` 代理清理

### 问题2：增量下载时涨跌幅全为 NULL

**现象**：下载单日数据后，所有股票的 pct_change 字段为 None。日报显示 0涨0跌，平均涨跌 NaN。

**根因**：

```
新浪数据源不提供涨跌幅字段，代码用 groupby().pct_change() 计算。
但增量下载只有 1 天新数据时，第一天没有前一天参照，pct_change() 返回 NaN。
如果下载 3 天数据 → 第一天 NaN，后两天正常。
如果只下载 1 天数据 → 全部 NaN。
```

**修复过程**：

```
尝试1：在 downloader 里用 fillna 补 → 单日数据时全 NaN，fillna 无效
尝试2：存完数据后用 SQL 从 DB 前一天收盘价反算 → ✅ 可行
实现：fix_pct_change() 函数，每次 download_all() 后自动执行
```

**教训**：

- 数据清洗必须在「数据完整」的基础上做，单行数据无法自计算
- 增量更新的边界条件（只有 1 天新数据）必须测试
- SQL 反算比 Python 计算更可靠（有完整的跨天数据）

---

### 问题3：日报指数与广度数据日期不匹配

**现象**：日报标题显示 6/9，广度数据显示 6/9，但指数数据显示的是 6/8。同一份报告中数据来自两天。

**根因**：

```
指数数据：从 AKShare API 实时拉取（可能有最新数据，也可能没有）
广度数据：从本地 SQLite 读取（固定是 DB 最新日期）

当 AKShare 的指数数据和 DB 的股票数据不是同一天时 → 错配
```

**修复过程**：

```
尝试1：让日报标注数据日期 → 只是标注，数据还是错的
尝试2：让指数 API 按 DB 日期查 → 找不到时回退最新
尝试3（最终）：所有指数统一用「最新日期中的最老值」
  - 比如 沪深300 有 6/9，深证成指 只有 6/8 → 全部用 6/8
  - 宁可全部用旧一天，也不能混用两天
```

**教训**：

- 多数据源的报告，必须统一数据时间点
- 标注错误不如防止错误

### 问题4：相同指数数据日期不一致

**现象**：6/9 日报中，深证成指用的是 6/8 数据，但创业板指用的是 6/9 数据。同一张表里指数来自两天。

**根因**：不同指数在 AKShare 的更新速度不同。深证成指可能 17:30 还没更新，创业板已经更新了。

**最终方案**（和问题3合并解决）：

```python
# 取所有指数最新日期的交集（最小值）
unified_date = min(df['date'].max() for df in index_data)
# 所有指数统一使用这个日期
```

### 问题5：部分股票下载失败，数据覆盖率不足

**现象**：300 只股票中只有 280 只有数据，20 只缺失。

**排查**：这 20 只不是停牌（同花顺可查到行情），是下载时被跳过了。

**根因**：下载器虽有 3 次重试，但遇到持续网络抖动时仍会遗漏。300 只 × 0.15s = 45 秒的下载过程中，部分请求可能恰好失败。

**修复**：加第二轮补漏——第一轮失败的股票在全部下载完后再集中重试（间隔 1 秒），成功率显著提高。

**教训**：

- 重试机制应该分两轮：快速重试 + 长间隔重试
- 下载完成后必须验证覆盖率（verify_data_quality）

---

### 问题6：服务器 SSH 连不上

**现象**：Claude Code 无法 SSH 到服务器，即使代理已关闭。

**根因**：macOS 系统级代理（Clash）配置在系统网络设置中，SSH 走系统代理，代理连不上目标。

**教训**：

- 开发环境应独立于系统的网络配置
- 远程操作命令应给用户自行执行，而非依赖 SSH 自动化

**现象**：cron 配置了 `>> logs/cron.log`，但 `logs/` 目录未创建，cron 执行失败无输出。

**修复**：在服务器部署时 `mkdir -p logs/`。

**教训**：

- 部署 checklist 必须包含所有目录创建
- 写一个 `setup.sh` 自动建目录（待做）

### 问题8：策略信号过多（噪声）

**现象**：3 个策略并行后，卖出信号 135 条，推送消息过长。

**根因**：卖出信号包含大量「建议卖出但实际未持有的股票」，对用户没有意义。

## 五、代码模式总结


```python

run.py:
    fix_pct_change()
    verify_data_quality()

    fix_pct_change()      # 再次修复（兜底）
    verify_data_quality() # 再次检查（兜底）
```

## 七、如果重来会怎么设计

1. **数据管道应该先完成**：先确保 300 只股票的完整历史数据在本地，再开始写策略。我们边写策略边修数据问题，多花了很多时间。
2. **指数数据应该进 DB**：4 个指数的日线应该和股票数据一起下载，彻底消除日期不一致。
3. **先单策略稳定再扩展**：双均线跑通后应该观察几天，再加速动量突破和均值回归。
4. **部署脚本化**：服务器的 Python 安装、目录创建、cron 配置应该一个 `setup.sh` 搞定，而不是手动逐步操作。
5. **回测引擎优先于策略**：应该在写策略之前就把回测引擎搭好（含蒙特卡洛），这样每个策略上线前都能立刻跑完整验证，而不是事后补课。
6. **参数集中化从第一天开始**：settings.py 是项目第一天就创建的，但直到 v0.2.0 审查才发现大量参数散落在外。应该从一开始就强制「所有可调数字必须进 settings」。
7. **文档目录从一开始就分类**：15 个文件平铺在 docs/ 根目录，找了 7 天才重构。第一天就应该建子目录。

### 问题9：Mac crontab 残留导致双重推送

**现象**：21:00 收到正确推送，23:00 又收到一次旧数据的推送。

**根因**：部署服务器后未清理 Mac 本地 `crontab -l` 中的旧定时任务。两个机器同时跑。

**修复**：`crontab -r` 清理 + 推送末尾加 `📍 主机名` 标识来源。

**教训**：部署审查必须包括「旧环境清理」，不能只检查新环境。

### 问题10：深证成指/创业板指数据日期不一致

**现象**：同一份日报中，深证成指显示 6/8 数据，创业板指显示 6/9 数据。

**根因**：不同指数在 AKShare 的更新速度不同。各自取「最新」导致日期不统一。

**修复**：`unified_date = min(各指数最新日期)`——统一取最老日期，保证一致性。

### 问题11：信号复盘永远返回空（隐藏 Bug）

**现象**：日报「昨日信号复盘」段从不显示数据。命中率统计功能完全失效。

**根因**：[analysis/stock.py:19-26](analysis/stock.py#L19-L26) 中 `conn.close()` 在第 19 行调用，但第 26 行仍将已关闭的连接传给 `_review_signals(conn)`。函数内部尝试查询 → 抛异常 → 被 `except Exception: return []` 静默吞掉。

**教训**：

- `try/except: return []` 是双刃剑——它防止了崩溃，但也埋藏了 bug
- SQLite 连接管理应遵循「谁打开谁关闭」原则，严禁跨作用域传已关闭的连接
- 写代码时要问自己：如果这段永远不执行，会发现吗？

### 问题12：广度全 NULL 时崩溃（隐藏 Bug）

### 问题15：回测性能瓶颈

**现象**：原始回测 3 种方案各自从头算策略信号，3 年数据跑 20 分钟，7 年预计 50 分钟。

**修复**：

```

  1. 所有策略信号只计算一次 → 存入 dict（128,570 条）
  2. 三种方案从同一信号池中按不同规则筛选
  3. 速度提升 ~40%（27 分钟跑完 7 年）
```

**关键代码模式**：`{(date, code, strategy_name, style): {action, strength, price}}`

**教训**：

- 回测优化的黄金法则：找到重复计算，抽出来只算一次
- 时间换空间在这里不值得——多花 100MB 内存缓存信号，省几十分钟

### 问题16：蒙特卡洛方法论迭代

**现象**：第一次实现的蒙特卡洛（交易顺序打乱）结果不变——因为乘法交换律，最终结果相同。第二次（逐笔 bootstrap）结果爆炸——个别极端交易被重复抽取导致结果失真。

**根因**：

```
尝试1：打乱交易顺序
  → 1.0 × A × B × C = 1.0 × C × B × A（乘法可交换）
  → 1000 次模拟全一样 → 无用

尝试2：有放回抽样逐笔交易
  → 盈利交易被重复抽到 → 指数爆炸
  → 亏损交易被漏掉 → 收益虚高
  → 中位数年化 +9183% → 不合理

尝试3（最终）：月度块 bootstrap
  → 交易按 20 笔一组切块（模拟月度）
  → 有放回抽块 → 保留块内相关性
  → 合理的结果：中位数 +113%，最差 5% -44%
```

**教训**：

- 蒙特卡洛不是简单地"随机打乱"——方法选择决定了结果是否有意义
- 块抽样 > 逐笔抽样——因为保留了真实市场的时间相关性
- 如果蒙特卡洛结果看起来太好了，那一定是方法有问题

### 问题20：Baostock 0.9.2 不兼容 Pandas 3.x 🔴

**现象**：修复多线程问题后，改为单线程顺序下载，仍然失败。报 `AttributeError: 'DataFrame' object has no attribute 'append'`。

**根因**：Baostock 0.9.2（最新版）的内部 `rs.get_data()` 方法使用了 `DataFrame.append()`，该方法在 Pandas 2.0 中被标记废弃，在 Pandas 3.0 中**被彻底移除**。项目环境使用的是 Pandas 3.0.3。

```python
# Baostock 内部代码（resultset.py L141）：
df = df.append(temp_df, ignore_index=True)
#     ^^^^^^ Pandas 3.x 中不存在
```

**修复**：在 `import baostock` 之前，给 `pd.DataFrame` 动态打补丁恢复 `append` 方法：

```python
def _make_append_compat():
    if not hasattr(pd.DataFrame, 'append'):
        def _append(self, other, ignore_index=False, sort=False):
            return pd.concat([self, other], ignore_index=ignore_index, sort=sort)
        pd.DataFrame.append = _append

_make_append_compat()
import baostock as bs  # ← 必须在补丁之后导入
```

**教训**：

- 老牌库（Baostock 2018年发布）很可能落后于快速演进的基础库（Pandas 3.x）
- `pip install` 成功 ≠ 代码能跑——需要真正调用 API 验证
- Monkey-patch 虽然不优雅，但在依赖库不更新时是唯一可行的方案
- 检查依赖兼容性应成为项目初始化的标准步骤

### 问题23：聚宽 get_price 多股票不能 skip_paused

**现象**：聚宽多因子回测策略报错：

```python
# 错误：
price_df = get_price(stocks, ..., skip_paused=True)

price_df = get_price(stocks, ...)  # 多股票时不能 skip_paused
```

### 问题24：聚宽 get_price 返回 Panel 导致因子全失效

### 问题25：get_price(panel=False)['close'] 返回 Series 而非 DataFrame

**现象**：优化版回测报 `AttributeError: 'Series' object has no attribute 'columns'`。`g.all_close` 即使传入了 300 只股票，`['close']` 索引后仍可能降维为 Series。

**根因**：`get_price(panel=False)` 返回的是 MultiIndex DataFrame `(field, stock)`。用 `['close']` 取子集时，pandas 的 `__getitem__` 在特定版本下会将单层列降维为 Series。这与 Pandas 版本和列数量有关，行为不一致。

**修复**：

```python
# 不直接用 ['close']，改用 .xs() 并强制保持 DataFrame
raw = get_price(stocks, ..., fields=['close', 'volume'], fq='pre', panel=False)
close_df = _ensure_df(raw.xs('close', axis=1, level=0))

def _ensure_df(x):
    return x.to_frame() if isinstance(x, pd.Series) else x
```

**教训**：

- MultiIndex DataFrame 的 `__getitem__` 行为因 Pandas 版本而异，`.xs()` 更可预测
- 从 MultiIndex 取子集后，始终检查 `type()` 是否为 DataFrame
- Series 没有 `.columns`——如果代码中任何地方假设结果为 DataFrame，加防护

8. **数据验证要查覆盖数不是总量**：`verify_data_quality()` 应该同时检查 `COUNT(DISTINCT code)` 和 `COUNT(*)`。572 条数据 × 2 只股票看起来"有数据"，实际上缺失了 99.3%。

## 九、2026-07-05 综合审查——28项问题，26项修复

### 最严重的5个发现

### 问题28：动量因子公式错误 🔴🔴🔴

**现象**：本地回测的多因子收益比聚宽系统性偏高 6-9pp。排查了数据源、权重、交易成本后仍不匹配。

**根因**：`engine/factors.py` 中动量因子的计算公式写错了。

```python
# 错误（本地用了数周）：
total_ret  = (close[-1] - close[-252]) / close[-252]    # 12个月总收益
recent_ret = (close[-1] - close[-21])  / close[-21]      # 最近1个月收益
momentum   = total_ret - recent_ret    # ❌ 这不是 12-1 动量！

# 正确（聚宽+学术标准）：
momentum = (close[-21] - close[-252]) / close[-252]     # ✅ 12-1 动量
```

**数学证明**：本地公式 = 聚宽公式 × (1 + 最近1月收益率)。只当最近一个月不涨不跌时两者巧合相等。

**影响**：所有动量排名都偏移了 (1+近月收益) 的倍数。最近涨得多的股票动量被高估，跌得多的被低估。聚合到月频选股后偏差被放大到 7pp。

**为什么这么久没发现**：本地回测从来不对标聚宽——没有参照系，没人知道它是错的。

**教训**：
- **回测代码必须有参照系**。单跑一个回测引擎，你怎么知道它对不对？
- 因子公式必须与学术标准或权威实现对照——不能自己推导
- 本地回测和云端回测结果差距 > 3pp 时，必须逐因子排查公式差异
- 这个 Bug 不是通过代码审查发现的——是因为对比了聚宽和本地同一策略的结果才暴露的

### 问题30：ROE 未来数据泄露 🔴🔴🔴

**现象**：ROE 接入后，本地回测收益从 14% 飙升到 19%——加了 15% 权重的有效因子收益应该更稳定才对。

**根因**：这是经典的 **Look-Ahead Bias（前视偏差）**。ROE 数据使用财报的"会计截止日"作为日期（如 `2020-06-30`），但半年报要到 8 月底才披露。回测在 7 月 1 日调仓时就用到了 Q2 ROE——这在现实中是不可能的。

**A股财报披露规则**：
```
Q1 (3/31) → 4/30前披露 → 实际可用 5月初   滞后 ~30天
Q2 (6/30) → 8/31前披露 → 实际可用 9月初   滞后 ~60天
Q3 (9/30) → 10/31前披露 → 实际可用 11月初  滞后 ~30天
Q4 (12/31) → 4/30前披露 → 实际可用 5月初   滞后 ~120天
```

**修复**：ROE 查询统一滞后 120 天。`WHERE date <= (target_date - 120 days)`。

**这是整个项目最隐蔽、最危险的 Bug**——它让回测收益虚高了 ~5pp，而且极难被发现。如果不是刻意排查"哪些数据有时间戳问题"，可能永远发现不了。

**教训**：
- **所有非实时数据必须确认 PIT（Point-in-Time）属性**。数据有两个时间戳：值日期（代表哪个时间点）和披露日期（何时公开）。回测必须用披露日期做切片。
- 国内免费数据源没有一个提供真正的 PIT 数据——必须自己实现滞后逻辑
- PE/PB 日频数据（Baostock 行情衍生）天然 PIT ✅，但季度财报数据不是 ❌
- PIT 检查应成为新数据源接入的标准步骤（已写入数据宪法）

### 问题31：本地回测 vs 聚宽回测不一致——根因分析

**现象**：TOP_N=5 时，本地年化 27.86% 但聚宽只有 3.12%（夏普为负）。信号方向完全相反——本地认为 TOP_N=5 最好，聚宽显示它几乎最差。

**根因分析（排除法）**：

| 修复项 | 修复后本地TOP_N=15 | 差距 |
|:--|:--|:--|
| 原始（多Bug） | 17% | +7pp |
| +动量公式修正 | 14.09% | +4pp |
| +ROE数据（未滞后） | 19.44% | +9.4pp ← 未来数据泄露 |
| +ROE 120天滞后 | 17.44% | +7.4pp |
| +佣金匹配聚宽 | 14.82% | +4.8pp |
| +数据扩展到1月 | 16.51% | +6.5pp |

**最终结论**：剩余 6.5pp 差距来自底层价格数据源不同（AKShare vs 聚宽数据商）。这不是可修复的差异——两个数据商的价格数据天然不同。

**多因子策略（排名选股）对微小差异极端敏感**：
- TOP_N=15：本地和聚宽前 15 重合度较高 → 结果接近（差距 ~6pp）
- TOP_N=5：本地和聚宽前 5 几乎没有重合 → 结果完全相反

**而三策略（硬阈值信号）不受此影响**：金叉就是金叉，均线交叉不依赖排名，AKShare 和聚宽的价格差异不足以改变交叉判断。

**教训**：
- **排名策略（如多因子 Z-score 后选前 N）不能在本地迭代**——必须直接在目标平台做
- 硬阈值策略（交叉、突破、超卖）本地迭代可靠
- 本地回测和云端回测的角色定位：
  - 本地 = 方向验证（改参数后方向对就行），仅限硬阈值策略
  - 聚宽 = 真理确认（绝对收益判断），排名策略必须
- 发现本地和云端不一致时，先对齐公式和数据，再接受不可消除的差异

## 十、2026-07-06 三策略优化 + 止损落地

### 问题33：三策略回撤过大——无止损机制 🟡

**现象**：双均线回撤 61.8%，动量突破回撤 66.0%，均值回归回撤 39.9%。即使参数优化后，回撤仍然在 30-60%。

**根因**：策略只有入场规则和出场规则（金叉买/死叉卖、突破买/跌破卖），没有硬止损。一旦方向判断错误，只能等反向信号触发——可能在 -30% 甚至 -50% 后才触发。

**修复**：加 5% 移动止损（从持仓期间最高点回落 5% 强制卖出）。回撤从 30-60% 降到 8-14%。

**落地实现**：
- `engine/position_tracker.py`——从 signal_history 推断当前持仓，检查止损触发
- `engine/runner.py`——每日自动生成 STOP_LOSS 信号，优先级最高
- `engine/risk_filter.py`——止损信号豁免 ST/股价/流动性拦截（仅拦跌停/停牌）

**教训**：
- 策略 = 入场 + 出场 + **止损**。缺了止损的策略不是完整策略
- 止损实现需要持仓追踪——而持仓追踪只需要 signal_history（已有），不需要新表
- 月频数据做止损有一定偏差（只能检查月末收盘价），但方向是正确的

---

### 问题34：参数网格搜索的局限性 🔴

**现象**：对三策略做 18 组参数 × 全量数据的网格搜索，选出"最优"参数。Walk-Forward 验证发现：
- 均线 MA(20,60)：训练集 24.5% → 验证集 0.3%（基本失效）
- 回归 BB(10,2.0)：训练集 -4.2% → 验证集 **40.7%**（完全反转！）

全量数据上的"最优"参数在验证集上表现糟糕或完全相反。

**根因**：这不是参数问题，是市场环境问题：
- 2019-2022 趋势市 → 趋势策略赚钱
- 2023-2024 震荡市 → 趋势策略亏钱，回归策略赚钱
- 策略表现 80% 取决于市场环境，20% 取决于参数

**教训**：
- **网格搜索选出的"最优"参数没有预测能力**——只是在特定历史区间上的事后最优

- 与其调参数，不如判断市场环境（趋势/震荡）——然后选择对应策略
- 参数优化应该找"稳健平台"（参数 ±20% 表现都稳定），而非"峰值"

### 问题35：仪表盘开发踩坑——JS 渲染 vs Python 直渲染

**现象**：仪表盘开发经历了 3 个版本：
- v1：JS fetch('data.json') → 文件协议不支持 → 白屏
- v2：数据嵌入 HTML 的 `<script>` 标签 + Chart.js CDN → JS 花括号和 Python f-string 冲突 → 语法错误 → 白屏
- v3：**Python 直接渲染 HTML**，零 JS 依赖 → 可用 ✅

**根因**：前两个版本都假设浏览器端能正常执行 JavaScript。但在实际使用中，CDN 可能被墙、JS 可能出错、文件协议有限制。任何 JS 错误都导致白屏——因为整个页面内容都是 JS 动态生成的。

**正确方案（v3）**：
- Python 直接查询 SQLite → 格式化为 HTML 字符串 → 写入文件
- 所有数据直接在 `<div>`、`<table>`、`<span>` 中
- 纯 CSS 样式（暗色主题，CSS Grid 布局）
- 零 JS 依赖——双击 HTML 即可打开，不需要服务器

**教训**：
- 内部工具（仪表盘、报告）应该优先用**服务端渲染**。Python 生成 HTML > JS 动态渲染
- "用 JS 框架做个好看的仪表盘"听起来很对，但会产生 3 层依赖（CDN → JS 执行 → DOM 操作），每一层都可能失败
- 单文件 HTML + 内嵌数据 = 最可靠的交付方式。双击即开，不需要任何环境
- 如果一定要用 JS 图表库，必须做 fallback：图表失败时至少显示表格数据
- f-string 中嵌套 JS 模板字面量（`${...}`）会导致花括号灾难——避免这种混合

```python
def _fetch_roe(conn, date: str) -> dict:
    from datetime import datetime, timedelta
    lagged = (datetime.strptime(date, '%Y-%m-%d')
              - timedelta(days=120)).strftime('%Y-%m-%d')
    df = pd.read_sql_query("""
        SELECT code, roe FROM financial_roe WHERE date <= ?
```

### 5.12 持仓追踪模式（零新表方案）

```python
# 不需要新建 positions 表——从 signal_history 推断持仓
# "最后一次 BUY 之后没有 SELL = 持仓中"

def get_positions() -> list[dict]:
    df = query("""
        SELECT code, name, date, action, price FROM signal_history
        WHERE status = 'passed' AND action IN ('BUY', 'SELL')
        ORDER BY code, date DESC
    """)
    positions = []
    for code, group in df.groupby('code'):
        if group.iloc[0]['action'] == 'BUY':  # 最新信号是BUY → 未卖
```

### 问题45：成分股列表每次调API导致 run.py 卡死 🔴🔴

| 项 | 内容 |
|----|------|
| **现象** | 服务器 `./venv/bin/python run.py` 在"获取沪深300成分股列表..."之后无限挂起，无任何报错 |
| **根因** | `fetch_hs300_constituents()` 没有检查 `stock_info` 表中已有的缓存数据，每运行都调 AKShare 的 `index_stock_cons_csindex()`。服务器网络到中证指数/东财接口偶尔不通，requests 没有超时设置，连接永远挂起 |
| **为什么这么久才暴露** | 之前在 Mac 上开发+测试，Mac 网络环境好（有代理），API 秒过。服务器是腾讯云内地机房，到这些数据源网站的网络不稳定 |
| **解决** | 改写 `fetch_hs300_constituents()`：① 优先从 `stock_info` 表读缓存（≥200行就跳过API）；② API调用加30秒 `signal.alarm` 超时保护；③ 超时/失败时降级到本地缓存 |
| **效果** | 每天运行从"调2个API→可能卡死"变成"读本地表→秒过"。99%的运行都不需要调API |
| **教训** | ① 低频变更数据（成分股半年调一次）不应该每次运行都调API——这是对网络和API的无效消耗；② Mac 上能跑 ≠ 服务器上能跑——网络环境完全不同；③ 任何网络调用必须有超时——没有超时的 `requests.get()` = 定时炸弹；④ "在本地跑得好好的"是最危险的假设 |


### 新增决策（2026-07-27）

**决策24：低频变更数据优先本地缓存**

成分股列表、交易日历、行业分类这类以月/半年为频率变更的数据，不应每次运行都调API。首次下载后存本地（SQLite表或CSV），后续运行从缓存读。有两个好处：① 消除网络依赖（服务器网络比开发机差很多）；② 跑得更快（读本地 vs 调远程API）。

**决策25：数据库 schema 必须自动迁移**

项目代码和数据库 schema 是一体的——代码改了列名/加新表/加新列，数据库必须跟着变。手工 ALTER TABLE 不可靠——忘了就崩一天。`ensure_schema()` 模式嵌入启动流程，每次运行自动检查+补列。代价是每次启动多 3 次 `PRAGMA table_info` 查询（< 10ms），收益是永远不会因为 schema 漂移而崩。

**决策26：密钥泄露后必须轮换（不只是删除消息）**

**决策27：Mac 能跑 ≠ 服务器能跑——网络假设必须验证**

开发机（Mac + 代理 + 国内网络）和服务器（腾讯云内地机房）的网络环境完全不同。任何依赖外部 API 的代码必须在目标环境测试过才算通过。不能假设"本地跑通了服务器也能跑"。

### 新增代码模式

**5.15 本地缓存 + 超时保护模式**

```python
# 适用：变更频率远低于运行频率的数据（成分股、交易日历、行业分类）
# 原则：1. 先读缓存 → 2. 必须调API时加超时 → 3. 失败降级到缓存

def fetch_data(force_refresh=False):
    # 第1层：缓存命中 → 直接返回（99%的情况）
    cached = read_from_local_cache()
    if cached and not force_refresh:
        return cached

    # 第2层：调API + 超时保护
    try:
        with timeout(30):  # signal.alarm / threading / httpx timeout
            result = call_remote_api()
        save_to_local_cache(result)
        return result
    except TimeoutError:
        # 第3层：降级
        if cached:
            log.warning("API超时，降级使用本地缓存")
            return cached
        raise  # 无缓存时不能降级，必须报错
```

**5.16 数据库自动迁移模式**

```python
# 适用：项目迭代中新增/修改数据库列
# 原则：期望 schema 声明式定义 + 启动时自动对齐

EXPECTED_SCHEMA = {
    'table_name': [
        ('col1', 'TEXT'),           # 列定义
        ('col2', 'REAL'),
        ('PRIMARY KEY', '(col1)'),  # 特殊约束
    ],
}

def ensure_schema():
    conn = sqlite3.connect(DB_PATH)
    for table, expected_cols in EXPECTED_SCHEMA.items():
        actual = {row[1] for row in conn.execute(f"PRAGMA table_info({table})")}
        for col_name, col_type in expected_cols:
            if col_name == 'PRIMARY KEY':
                continue  # SQLite不支持ALTER TABLE ADD PRIMARY KEY
            if col_name not in actual:
                conn.execute(f"ALTER TABLE {table} ADD COLUMN {col_name} {col_type}")
                print(f"  ✅ 迁移: {table} +{col_name} {col_type}")
    conn.commit()
```

优点：新增列只需改 `EXPECTED_SCHEMA` 字典，服务器 `git pull` 后自动生效。零手工，零遗忘风险。

局限性：SQLite 不支持 `ALTER TABLE DROP COLUMN`（需重建表）、不支持修改列类型。对简单场景（加列）完美覆盖，对复杂迁移（删列、改类型）需要额外处理。

**5.17 信号对象规范化模式**

```python
# 不同来源的信号对象 key 名不一致 → KeyError
# 解决：统一入口做规范化

SIGNAL_KEY_MAP = {
    'code': 'stock_code',
    'name': 'stock_name',
}

def normalize_signal(sig: dict) -> dict:
    """统一信号对象的 key 名，消除不同来源的差异"""
    for old_key, new_key in SIGNAL_KEY_MAP.items():
        if old_key in sig and new_key not in sig:
            sig[new_key] = sig.pop(old_key)
    return sig
```

## 十七、2026-08-02~09 仪表盘自动更新排查——部署链路终点验证

### 阶段概述

### 问题55：CDN 缓存不遵循源站 max-age 🟡

| 项 | 内容 |
|----|------|
| **现象** | 上传带 `Cache-Control: max-age=300` 后，`/quant/` 路径线上仍返回旧文件（`last-modified: 02 Aug`），需手动刷新 CDN 才更新；`/works/quant/` 路径则自动更新正常 |
| **根因** | CDN 节点缓存规则优先级高于源站 Cache-Control。历史文件（早期上传无缓存头）被节点按默认规则长期缓存；新文件带 max-age 后是否生效取决于该路径的节点缓存配置 |
| **解决** | ① 新上传统一带 `-H '{"Cache-Control":"max-age=300"}'` ② 历史遗留路径手动刷新一次 CDN 清旧缓存 ③ 之后节点按 5 分钟过期自动回源 |
| **教训** | 源站 Cache-Control 不一定被 CDN 遵循——验证缓存行为要看 CDN 响应头（`x-cache-lookup: HIT/MISS`、`last-modified`），并保留"最后手动刷新一次"的收尾动作 |

博客 iframe 指向量化路径、量化上传路径依赖博客目录结构——这类跨项目耦合要记录在双方文档中（本复盘 + 部署指南），并注明"改路径时两边要同步"。

**决策34：历史遗留路径要么弃用要么持续同步**

路径迁移（如 `/quant/` → `/works/quant/`）时，旧路径上被外部引用（iframe/书签）的文件要么重定向、要么持续同步，不能只传新路径——否则外部引用永远看到旧数据。

## 十八、2026-08-16 手机端永久旧数据——死文件 + CDN 缓存规则变更残留

### 阶段概述

仪表盘增强上线一周后，用户报告：**电脑显示 8-14 数据，手机永远显示 8-07 数据**。线上 curl 检查（带斜杠路径）显示一切正常、数据是新的——与上次（问题53）同款陷阱：**验证了"服务器视角"和"电脑视角"，没验证"手机视角"的 URL**。最终定位为两个叠加根因：一个 8-09 手动部署时制造、此后无人更新的"死文件" `quant.html`，加上 CDN 缓存规则变更不清理已有条目导致的多节点缓存不一致。

### 问题57：手动部署副本脱离生成器——quant.html 死文件 🔴🔴

| 项 | 内容 |
|----|------|
| **现象** | 手机收藏/输入 `xolnxoln.cn/works/quant`（无斜杠）永远显示 8-07 数据；电脑访问带斜杠 `works/quant/` 显示 8-14 |
| **根因** | COS ".html 省略"规则：无斜杠 URL 命中 `works/quant.html` 文件（不是目录里的 index.html）。8-09 手动部署时为了支持无斜杠访问，复制了一份 `quant.html`（数据 8-07）。此后 cron 每天执行 `coscmd upload -r web/output/ /works/quant/ --delete` 上传整个目录，但 **generate.py 从不生成 quant.html，目录上传自然永远不包含它**——这个文件成了"手动制造、无人更新"的死文件，其内容被 CDN 按默认策略长缓存，30 天不过期不回源 |
| **解决** | ① 立即：服务器 `coscmd upload web/output/index.html /works/quant.html` 手动同步 ② 治本：`web/generate.py` 的 `build()` 把 `page_index()` 结果同时写入 `index.html` 与 `quant.html`（同一变量写两个文件，构造上保证字节级一致），cron 目录上传自动覆盖，永不复发 ③ 顺手清理同类隐患：删除 `web/output/data.json`（2026-07-05 重构前旧生成器残留，全仓搜索无引用，同样永不更新） |
| **教训** | **所有对外 URL 的入口文件必须由生成器产出**。任何"手动上传一次"的文件（副本、改名、调整）都是未来的死文件——它脱离了自动化链路，迟早成为陈旧数据的来源。排查时对每个 URL 问一句："这个文件是谁生成/更新的？" 回答不了就是隐患 |

### 问题58：CDN 规则变更不清已有缓存条目——多节点缓存不一致 🟡

| 项 | 内容 |
|----|------|
| **现象** | 同一个 URL `/quant/index.html` 两次 curl 分别返回 8-09 与 8-14 版本（`last-modified` 不同）；源站对象本身已是最新（8-14 13:20） |
| **根因** | 8-09 配置 CDN 规则（`max-age=300`）**只影响规则变更后新建的缓存条目**；规则变更前上传的对象（8-09 部署时）已被节点按默认策略（长缓存）缓存，条目未过期前不回源验证。不同边缘节点首次缓存时间不同 → 部分节点 8-09 旧版、部分节点已回源新版，表现就是"同一个 URL 结果随机" |
| **解决** | CDN 控制台"刷新预热"刷掉所有相关 URL 的旧条目（本次刷 5 个：`/works/quant.html`、`/works/quant/index.html`、`/works/quant/`、`/quant/index.html`、`/quant/`），刷新后各节点回源拿新版本 |
| **教训** | ① CDN 规则变更 ≠ 已有缓存失效——**改规则后必须主动刷新历史条目**，否则新旧节点并存、结果随机 ② 排查"为什么有的设备新有的设备旧"时，怀疑点包括：不同 URL（路径/无斜杠）、不同缓存节点、不同设备缓存——用**URL 矩阵**逐个验证才能定位 |

### 问题59：手机与电脑的访问链路天然不同 🟡

| 项 | 内容 |
|----|------|
| **现象** | 电脑直接访问带斜杠 URL → 新数据；手机从博客 iframe（`/quant/index.html`）或无斜杠收藏进入 → 旧数据 |
| **根因** | 手机与电脑的入口不同：电脑通常访问地址栏里显式输入的路径，手机多走博客 iframe / 收藏夹 / 微信链接——这些入口指向的 URL 与电脑不同，缓存状态和命中的对象也不同 |
| **解决** | 验证时**同时抓用户所有可能的入口 URL**（博客 iframe 指向 + 无斜杠 + 带斜杠 + 显式 index.html），逐一比对 `last-modified` 与内容标记 |
| **教训** | "电脑正常"不能推断"手机正常"。部署验证的 URL 列表 = 用户实际使用的全部入口，不是其中一个 |

### 新增决策（2026-08-16）

**决策35：对外 URL 的入口文件必须由生成器统一产出，禁止手动副本**

任何被外部引用（iframe、收藏夹、书签、分享链接）的 URL，其命中的文件必须来自自动化生成链路（generate.py → cron 上传）。手动复制、改名、一次性上传 = 死文件，必然成为陈旧数据源。生成器用"同一变量写多个文件"保证多入口字节级一致，杜绝二次维护漂移。

**决策36：CDN 缓存规则变更后必须手动刷新历史条目**

配置 CDN 规则（max-age、缓存时间）只影响变更后的新缓存。规则变更前已缓存的条目按旧规则继续存活（可能 30 天），造成多节点新旧并存。改规则后立即在控制台刷新受影响的 URL/目录，并纳入"部署收尾清单"。

**决策37：部署验证用 URL 矩阵覆盖所有入口**

验证收尾 = 对用户全部入口 URL 逐个执行 `curl -sI`（看 `last-modified`）+ `curl -s`（看内容标记），不能只验证其中一个。入口清单：带斜杠目录、无斜杠路径、显式 index.html、博客 iframe 指向路径。

### 新增代码模式

**5.20 多入口 URL 矩阵验证模式**

```bash
# 对一个入口的验证 = 响应头版本 + 内容标记，两个都查
for u in "https://xolnxoln.cn/works/quant" "https://xolnxoln.cn/works/quant/" \
         "https://xolnxoln.cn/works/quant/index.html" "https://xolnxoln.cn/quant/index.html" \
         "https://xolnxoln.cn/quant/"; do
  echo "=== $u ==="
  curl -sI -m 15 "$u" | grep -iE '^(HTTP|last-modified)'
  curl -s -m 15 "$u" | grep -oE '数据: 2026-[0-9-]+' | head -1
done
```

适用：所有多入口静态站点部署的收尾验证（本项目 5 个入口）。扩展"5.19 终点验证"：不止验证一个 URL，而是验证**用户会用到的所有 URL**。

**5.21 死文件审计模式**

```bash
# 找出"线上有、生成器不产出"的文件（死文件候选）
# 生成器产出的文件名（generate.py build() 的 pages 列表）vs 服务器 web/output/ 实际内容
ls web/output/ | sort > /tmp/local.txt
# 服务器：coscmd list /works/quant/ | 对比
# 再全仓 grep 引用，无引用的直接删除（本次删除了 data.json）
```

适用：每次部署前快速审计；发现"只在线上存在、无生成代码"的文件即处理（删除或接入生成流程）。
