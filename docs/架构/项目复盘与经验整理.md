## ⚠️ 遇到问题时的自动化 Skill 操作流程

> 2026-06-18 确立——聚宽策略8次报错×2天浪费的根本教训。

**不要手动瞎改。不要凭猜测修。按以下流程自动执行：**

```
遇到任何问题（报错/异常/数据不对）
    │
    ▼
Step 1: 诊断
  /verify 或 debugging-and-error-recovery
  → 系统排查根因（不是猜，是逐层排除）
    │
    ▼
Step 2: 调研（如果涉及不熟悉的平台/API）
  /deep-research 或 WebSearch
  → 搜索官方文档 + 社区最佳实践 + 已知坑点
  → 输出 "XXX编码须知" 文档
    │
    ▼
Step 3: 验证假设
  写 ≤10 行最小验证脚本
  → 在目标环境实测，确认 API 行为的真相
  → 以实测为准（文档可能过时！）
    │
    ▼
Step 4: 制定方案
  spec-driven-development
  → 基于验证结果写数据流，标注每一步的类型转换
    │
    ▼
Step 5: 分步实现
  incremental-implementation
  → 每一步验证通过再走下一步
    │
    ▼
Step 6: 审查
  /code-review 或 code-review-and-quality
  → 对照审查规范逐项检查
```

**禁止的行为**：
- ❌ 报错 → 改一行 → 再跑 → 又报错 → 再改（"修一下再跑"循环）
- ❌ 凭记忆/经验假设 API 返回格式（"应该是宽表吧"）
- ❌ 不跑环境验证就写完整代码
- ❌ 2次以上同类报错还不质疑底层假设

**触发条件**：只要满足以下任一条件，立即启动上述流程：
- 同一个问题出现 2 次以上
- 涉及新平台/新 API
- 不确定数据格式
- 回测结果异常（收益0%或极高）

## 二、遇到的问题与解决方案（按发生顺序）

### 问题1：AKShare 东方财富 API 全部连不上

**现象**：首次 `run.py --init` 下载 300 只股票，全部失败。报 `ProxyError`。

**排查过程**：
```
1. 怀疑代理 → 检查系统代理（Clash on 127.0.0.1:7897）
2. 关代理 → 仍然失败，报 SSL 证书错误
3. 发现 Python 3.14 缺少根证书 → 运行 Install Certificates.command 修复
4. SSL 修复后 → 还是连不上，报 RemoteDisconnected
5. curl 测试 → 能用但 Python 不行 → 怀疑 TLS 或 IP 问题
6. 换数据源 → 新浪 source 能用 ✅
```

**根因**：多层叠加——代理拦截 + SSL 证书缺失 + 东方财富 API 不稳定。

**最终方案**：优先用新浪数据源（`stock_zh_a_daily`），东方财富作备用。新浪稳定且不需要额外配置。

**教训**：
- 数据源必须有备份，不能依赖单一 API
- 启动时清除代理环境变量
- 在 downloader.py 开头加 `os.environ` 代理清理

### 问题2：增量下载时涨跌幅全为 NULL

**现象**：下载单日数据后，所有股票的 pct_change 字段为 None。日报显示 0涨0跌，平均涨跌 NaN。

**根因**：
```
新浪数据源不提供涨跌幅字段，代码用 groupby().pct_change() 计算。
但增量下载只有 1 天新数据时，第一天没有前一天参照，pct_change() 返回 NaN。
如果下载 3 天数据 → 第一天 NaN，后两天正常。
如果只下载 1 天数据 → 全部 NaN。
```

**修复过程**：
```
尝试1：在 downloader 里用 fillna 补 → 单日数据时全 NaN，fillna 无效
尝试2：存完数据后用 SQL 从 DB 前一天收盘价反算 → ✅ 可行
实现：fix_pct_change() 函数，每次 download_all() 后自动执行
```

**教训**：
- 数据清洗必须在「数据完整」的基础上做，单行数据无法自计算
- 增量更新的边界条件（只有 1 天新数据）必须测试
- SQL 反算比 Python 计算更可靠（有完整的跨天数据）

---

### 问题3：日报指数与广度数据日期不匹配

**现象**：日报标题显示 6/9，广度数据显示 6/9，但指数数据显示的是 6/8。同一份报告中数据来自两天。

**根因**：
```
指数数据：从 AKShare API 实时拉取（可能有最新数据，也可能没有）
广度数据：从本地 SQLite 读取（固定是 DB 最新日期）

当 AKShare 的指数数据和 DB 的股票数据不是同一天时 → 错配
```

**修复过程**：
```
尝试1：让日报标注数据日期 → 只是标注，数据还是错的
尝试2：让指数 API 按 DB 日期查 → 找不到时回退最新
尝试3（最终）：所有指数统一用「最新日期中的最老值」
  - 比如 沪深300 有 6/9，深证成指 只有 6/8 → 全部用 6/8
  - 宁可全部用旧一天，也不能混用两天
```

**教训**：
- 多数据源的报告，必须统一数据时间点
- 标注错误不如防止错误

### 问题4：相同指数数据日期不一致

**现象**：6/9 日报中，深证成指用的是 6/8 数据，但创业板指用的是 6/9 数据。同一张表里指数来自两天。

**根因**：不同指数在 AKShare 的更新速度不同。深证成指可能 17:30 还没更新，创业板已经更新了。

**最终方案**（和问题3合并解决）：
```python
# 取所有指数最新日期的交集（最小值）
unified_date = min(df['date'].max() for df in index_data)
# 所有指数统一使用这个日期
```

### 问题5：部分股票下载失败，数据覆盖率不足

**现象**：300 只股票中只有 280 只有数据，20 只缺失。

**排查**：这 20 只不是停牌（同花顺可查到行情），是下载时被跳过了。

**根因**：下载器虽有 3 次重试，但遇到持续网络抖动时仍会遗漏。300 只 × 0.15s = 45 秒的下载过程中，部分请求可能恰好失败。

**修复**：加第二轮补漏——第一轮失败的股票在全部下载完后再集中重试（间隔 1 秒），成功率显著提高。

**教训**：
- 重试机制应该分两轮：快速重试 + 长间隔重试
- 下载完成后必须验证覆盖率（verify_data_quality）

---

### 问题6：服务器 SSH 连不上

**现象**：Claude Code 无法 SSH 到服务器，即使代理已关闭。

**根因**：macOS 系统级代理（Clash）配置在系统网络设置中，SSH 走系统代理，代理连不上目标。

**教训**：
- 开发环境应独立于系统的网络配置
- 远程操作命令应给用户自行执行，而非依赖 SSH 自动化

**修复**：在服务器部署时 `mkdir -p logs/`。

**教训**：

## 五、代码模式总结

### 5.1 数据修复模式

```python
# 下载 → 修复 → 验证 的标准流程
download_all()        # 拉数据
fix_pct_change()     # 修数据
verify_data_quality() # 查数据
```

### 5.2 双重保障模式

```python
# run.py 和 report.py 各自独立执行数据检查
# 一个挂不影响另一个
run.py:
    fix_pct_change()
    verify_data_quality()

report.py:
    fix_pct_change()      # 再次修复（兜底）
    verify_data_quality() # 再次检查（兜底）
```

### 5.3 API 降级模式

```python
# 永远有备用方案
def download_stock_history():
    # 方案1：新浪（稳定，主用）
    df = ak.stock_zh_a_daily(...)
    if df is None:
        # 方案2：东方财富（备用）
        df = ak.stock_zh_a_hist(...)
    return df
```

### 5.4 静默 + 告警模式

```python
# 数据异常时不显示假数据，而是明确告警
if pct_change 全 NULL:
    return {'data_error': '涨跌幅数据全部缺失'}  # 不返回 0涨0跌
```

## 七、如果重来会怎么设计

1. **数据管道应该先完成**：先确保 300 只股票的完整历史数据在本地，再开始写策略。我们边写策略边修数据问题，多花了很多时间。

2. **指数数据应该进 DB**：4 个指数的日线应该和股票数据一起下载，彻底消除日期不一致。

3. **先单策略稳定再扩展**：双均线跑通后应该观察几天，再加速动量突破和均值回归。

4. **部署脚本化**：服务器的 Python 安装、目录创建、cron 配置应该一个 `setup.sh` 搞定，而不是手动逐步操作。

5. **回测引擎优先于策略**：应该在写策略之前就把回测引擎搭好（含蒙特卡洛），这样每个策略上线前都能立刻跑完整验证，而不是事后补课。

6. **参数集中化从第一天开始**：settings.py 是项目第一天就创建的，但直到 v0.2.0 审查才发现大量参数散落在外。应该从一开始就强制「所有可调数字必须进 settings」。

7. **文档目录从一开始就分类**：15 个文件平铺在 docs/ 根目录，找了 7 天才重构。第一天就应该建子目录。

### 问题9：Mac crontab 残留导致双重推送

**现象**：21:00 收到正确推送，23:00 又收到一次旧数据的推送。

**根因**：部署服务器后未清理 Mac 本地 `crontab -l` 中的旧定时任务。两个机器同时跑。

**修复**：`crontab -r` 清理 + 推送末尾加 `📍 主机名` 标识来源。

**教训**：部署审查必须包括「旧环境清理」，不能只检查新环境。

### 问题10：深证成指/创业板指数据日期不一致

**现象**：同一份日报中，深证成指显示 6/8 数据，创业板指显示 6/9 数据。

**根因**：不同指数在 AKShare 的更新速度不同。各自取「最新」导致日期不统一。

**修复**：`unified_date = min(各指数最新日期)`——统一取最老日期，保证一致性。

### 问题11：信号复盘永远返回空（隐藏 Bug）

**现象**：日报「昨日信号复盘」段从不显示数据。命中率统计功能完全失效。

**根因**：[analysis/stock.py:19-26](analysis/stock.py#L19-L26) 中 `conn.close()` 在第 19 行调用，但第 26 行仍将已关闭的连接传给 `_review_signals(conn)`。函数内部尝试查询 → 抛异常 → 被 `except Exception: return []` 静默吞掉。

**教训**：
- `try/except: return []` 是双刃剑——它防止了崩溃，但也埋藏了 bug
- SQLite 连接管理应遵循「谁打开谁关闭」原则，严禁跨作用域传已关闭的连接
- 写代码时要问自己：如果这段永远不执行，会发现吗？

### 问题12：广度全 NULL 时崩溃（隐藏 Bug）

**现象**：当 `pct_change` 全 NULL 时，广度分析整个消失。

**根因**：[analysis/macro.py:143](analysis/macro.py#L143) 中引用了不存在的变量 `max_date`（实际变量名是 `data_date`），触发 `NameError` → 被外层 `except: return {}` 吞掉。

**教训**：同上——`try/except` 掩盖的 bug 比 crash 更可怕。crash 至少你能发现。

### 问题13：参数散落各处

**现象**：止损比例、仓位上限、数据加载天数、质量检查阈值等关键参数硬编码在各个源文件中，调参需要在多处修改。

**修复**：所有参数集中到 `config/settings.py`：
- 均值回归参数（`BB_PERIOD`, `BB_STD_DEV`）
- 仓位档位表（`POSITION_TIERS`）——用 `(上限, 单票%, 止损%, 持仓数)` 元组数组
- 策略运行器参数（`STRATEGY_DATA_DAYS`, `SELL_SIGNAL_LIMIT`）
- 数据质量阈值（`MIN_STOCK_COUNT`, `MIN_SECTOR_COUNT`, `MAX_EXTREME_PCT`）

**教训**：
- 项目初期"先写死再抽离"是正常的，但到 v0.2 必须集中化
- 用元组数组替代 if/elif 链，新增档位加一行即可

### 问题14：回测结论被数据区间彻底颠覆

**现象**：3 年回测（2023-2026）显示「择时改善 +14pp」，7 年回测（2019-2026）显示「择时恶化 -5pp」。

**根因**：
```
3 年数据 = 只覆盖了熊市（49% 弱势日）
  → 择时在熊市中表现英勇（躲过大跌）
  → 结论：择时是最大 Alpha 来源

7 年数据 = 覆盖完整牛熊（2019-2020 大牛市）
  → 择时在牛市中踏空了（均线滞后）
  → 结论：择时保护了熊市但害了牛市，净效果略负
```

**教训**：
- **少于 5 年的回测结论不可靠**——可能只覆盖了半个周期
- 绝不能根据短期回测做决策——你只会看到你想看到的
- 2019 年的牛市是 2023-2026 熊市的对称面——两者都必须看

### 问题15：回测性能瓶颈

**现象**：原始回测 3 种方案各自从头算策略信号，3 年数据跑 20 分钟，7 年预计 50 分钟。

**根因**：每种方案（无择时/二元择时/权重匹配）独立运行策略计算，但 95% 的计算量（策略信号生成）完全相同——只是在不同的过滤规则下反复算同样的事。

**修复**：
```
引入「预计算 + 复用」架构：
  1. 所有策略信号只计算一次 → 存入 dict（128,570 条）
  2. 三种方案从同一信号池中按不同规则筛选
  3. 速度提升 ~40%（27 分钟跑完 7 年）
```

**关键代码模式**：`{(date, code, strategy_name, style): {action, strength, price}}`

**教训**：
- 回测优化的黄金法则：找到重复计算，抽出来只算一次
- 时间换空间在这里不值得——多花 100MB 内存缓存信号，省几十分钟

### 问题16：蒙特卡洛方法论迭代

**现象**：第一次实现的蒙特卡洛（交易顺序打乱）结果不变——因为乘法交换律，最终结果相同。第二次（逐笔 bootstrap）结果爆炸——个别极端交易被重复抽取导致结果失真。

**根因**：
```
尝试1：打乱交易顺序
  → 1.0 × A × B × C = 1.0 × C × B × A（乘法可交换）
  → 1000 次模拟全一样 → 无用

尝试2：有放回抽样逐笔交易
  → 盈利交易被重复抽到 → 指数爆炸
  → 亏损交易被漏掉 → 收益虚高
  → 中位数年化 +9183% → 不合理

尝试3（最终）：月度块 bootstrap
  → 交易按 20 笔一组切块（模拟月度）
  → 有放回抽块 → 保留块内相关性
  → 合理的结果：中位数 +113%，最差 5% -44%
```

**教训**：
- 蒙特卡洛不是简单地"随机打乱"——方法选择决定了结果是否有意义
- 块抽样 > 逐笔抽样——因为保留了真实市场的时间相关性
- 如果蒙特卡洛结果看起来太好了，那一定是方法有问题

### 问题19：财务数据缺失 99.3%——多线程登录Bug 🔴

**现象**：`financial_data` 表只有 572 行，覆盖仅 2 只股票（001391、600930）。多因子引擎的价值因子（PE/PB, 20%权重）和质量因子（ROE, 15%权重）完全失效。这个 Bug 从 6/14 财务下载器上线起就存在，**无声无息地跑了 3 天没有发现**。

```
1. 初步怀疑 AKShare 网络不稳定 → 换 Baostock

5. 结论：Baostock 的 login() 状态不跨线程共享
```

```python
with ThreadPoolExecutor(max_workers=8) as pool:
    pool.submit(download_one, code)  # ← 子线程没有登录状态！
    # 298/300 只股票静默失败
```

**影响**：
- 多因子引擎的 PE/PB/ROE 因子值全为 0，仅靠 4 个纯价格因子（65% 权重）
- 之前一直误判为"AKShare 网络问题"，浪费了排查方向

**教训**：
- **下载完必须验证覆盖率**：`verify_financial_data()` 存在但只看总量和 NULL 率，不看 `COUNT(DISTINCT code)`
- 不能只看"有数据"就认为"数据 OK"——必须查股票覆盖数
- **多线程 + 有状态连接 = 灾难配方**。C 扩展库的登录状态几乎从不跨线程共享
- 当某个模块被长期标记为"待重试"时，应该主动审查为什么重试一直失败

### 问题20：Baostock 0.9.2 不兼容 Pandas 3.x 🔴

**现象**：修复多线程问题后，改为单线程顺序下载，仍然失败。报 `AttributeError: 'DataFrame' object has no attribute 'append'`。

**根因**：Baostock 0.9.2（最新版）的内部 `rs.get_data()` 方法使用了 `DataFrame.append()`，该方法在 Pandas 2.0 中被标记废弃，在 Pandas 3.0 中**被彻底移除**。项目环境使用的是 Pandas 3.0.3。

```python
# Baostock 内部代码（resultset.py L141）：
df = df.append(temp_df, ignore_index=True)
#     ^^^^^^ Pandas 3.x 中不存在
```

**修复**：在 `import baostock` 之前，给 `pd.DataFrame` 动态打补丁恢复 `append` 方法：

```python
def _make_append_compat():
    if not hasattr(pd.DataFrame, 'append'):
        def _append(self, other, ignore_index=False, sort=False):
            return pd.concat([self, other], ignore_index=ignore_index, sort=sort)
        pd.DataFrame.append = _append

_make_append_compat()
import baostock as bs  # ← 必须在补丁之后导入
```

**教训**：
- 老牌库（Baostock 2018年发布）很可能落后于快速演进的基础库（Pandas 3.x）
- `pip install` 成功 ≠ 代码能跑——需要真正调用 API 验证
- Monkey-patch 虽然不优雅，但在依赖库不更新时是唯一可行的方案
- 检查依赖兼容性应成为项目初始化的标准步骤

### 问题23：聚宽 get_price 多股票不能 skip_paused

**现象**：聚宽多因子回测策略报错：
```
ParamsError: get_price 取多只股票数据时, 为了对齐日期, 不能跳过停牌
```

**根因**：`get_price()` 传入多只股票时，如果使用 `skip_paused=True`，不同股票的停牌日不同，无法对齐所有股票的日期矩阵。聚宽强制要求多股票时必须保留停牌日（返回 NaN）。

**修复**：去掉 `skip_paused=True`。后续在逐股票处理时，`close_series.dropna()` 自动跳过 NaN 值，不影响因子计算。

```python
# 错误：
price_df = get_price(stocks, ..., skip_paused=True)

# 正确：
price_df = get_price(stocks, ...)  # 多股票时不能 skip_paused
```

**教训**：
- 平台 API 的约束条件是写死的，不能凭直觉
- 之前本地策略的 cleaner.py 也做过停牌标记——但如果一开始就参考本地经验写聚宽代码，应该注意到"批量加载时停牌处理应该在单股逻辑里做"
- 跨平台代码要在目标平台跑一次最简单的调用验证环境，而不是完整写完再测

### 问题24：聚宽 get_price 返回 Panel 导致因子全失效

**现象**：回测能跑了但每月都报 `WARNING - 有效得分过少`。策略收益 0.00%，始终空仓。日志同时有 `UserWarning: 不建议继续使用panel`。

**根因**：`get_price()` 默认返回 Pandas Panel 对象（已被废弃）。高版本 Pandas 中 Panel 的数据访问行为异常，`price_df['close'][stock]` 取不到数据或取到错误维度，导致所有股票的因子计算失败（`close_series < 60` 被跳过）。

**修复**：加 `panel=False`——让 `get_price()` 返回 MultiIndex DataFrame（Pandas 现代标准格式）：

```python
price_df = get_price(stocks, ..., panel=False)  # 一行修复
```

**教训**：
- 平台 API 的废弃警告不要忽略——它不仅是"风格问题"，可能直接导致功能失效
- 警告信息里的参数（`panel=False`）就是正确答案，照做就行
- 所有聚宽代码都应该加 `panel=False`——包括之前的三策略回测模板

### 问题25：get_price(panel=False)['close'] 返回 Series 而非 DataFrame

**现象**：优化版回测报 `AttributeError: 'Series' object has no attribute 'columns'`。`g.all_close` 即使传入了 300 只股票，`['close']` 索引后仍可能降维为 Series。

**根因**：`get_price(panel=False)` 返回的是 MultiIndex DataFrame `(field, stock)`。用 `['close']` 取子集时，pandas 的 `__getitem__` 在特定版本下会将单层列降维为 Series。这与 Pandas 版本和列数量有关，行为不一致。

**修复**：
```python
# 不直接用 ['close']，改用 .xs() 并强制保持 DataFrame
raw = get_price(stocks, ..., fields=['close', 'volume'], fq='pre', panel=False)
close_df = _ensure_df(raw.xs('close', axis=1, level=0))

def _ensure_df(x):
    return x.to_frame() if isinstance(x, pd.Series) else x
```

**教训**：
- MultiIndex DataFrame 的 `__getitem__` 行为因 Pandas 版本而异，`.xs()` 更可预测
- 从 MultiIndex 取子集后，始终检查 `type()` 是否为 DataFrame
- Series 没有 `.columns`——如果代码中任何地方假设结果为 DataFrame，加防护

### 问题26：get_price(panel=False) 实际返回长格式——所有假设全错 🔴🔴🔴

**现象**：环境验证脚本揭示真相——`get_price(panel=False)` 返回的 DataFrame 列名是 `['time', 'code', 'close']`，而非我们假设的"columns=股票, index=日期"宽表。从第1版到第7版的所有代码逻辑——`.loc[:date]`、`.columns`取交集、`.iloc[-260:]`全隐含宽表假设，全部错误。

**时间线**：
```
第1版：假设 panel=False 返回宽表 → columns 取交集失败 → 改格式匹配
第2-3版：Panel废弃、xs()兼容 → 还是取不到
第4版：缓存方案 → initialize取不到未来数据 → 空仓
第5版：每月拉取+MultiIndex处理 → columns格式不对 → 0操作
第6版：环境验证4个Cell → 最后才发现真相
第7版（正确）：.pivot() 转宽表 → 全部逻辑由此往下
```

**根因**：每一版都在"修复上一版的报错"，但没有一版停下来问："我对 API 返回格式的假设正确吗？"

**修复**：

```python
# 真相（2026-06-18 实测）：
raw = get_price(stocks, ..., panel=False)
# columns = ['time', 'code', 'close']  ← 长格式！

# 正确用法：
close_wide = raw.pivot(index='time', columns='code', values='close')
# → index=date, columns=stocks → 后续逻辑全部基于此
```

**教训**（这个问题的教训是整个复盘文档中最重要的）：
- **不要假设 API 的返回格式。测它。** 5行代码就能知道真相
- 反复报错 → 停下 → 质疑最底层的假设 → 验证 → 再继续
- "修一下报错再跑"的循环是最大的时间黑洞
- 跨平台代码必须在目标平台上跑一次最小环境验证：`print(type(), columns, shape)`

### 5.7 Pandas 兼容补丁模式

```python
# 老库 + 新 Pandas 的兼容方案：
# 在 import 老库之前，给被移除的方法打补丁

def _make_append_compat():
    if not hasattr(pd.DataFrame, 'append'):
        def _append(self, other, ignore_index=False, sort=False):
            return pd.concat([self, other], ignore_index=ignore_index, sort=sort)
        pd.DataFrame.append = _append

_make_append_compat()
import baostock as bs  # ← 必须在补丁之后导入
```

适用场景：依赖库使用了 Pandas 2.0+ 中移除的 API
注意事项：补丁必须在该库 `import` 之前执行
局限性：只恢复方法签名，某些边缘参数可能不支持

## 如果重来会怎么设计（续）

8. **数据验证要查覆盖数不是总量**：`verify_data_quality()` 应该同时检查 `COUNT(DISTINCT code)` 和 `COUNT(*)`。572 条数据 × 2 只股票看起来"有数据"，实际上缺失了 99.3%。

9. **新模块上线必须有 end-to-end 测试**：财务下载器 6/14 写完就合入了，没有跑一次 `SELECT COUNT(DISTINCT code)` 验证。如果上线时多花 30 秒查一下数据库，3 天后就不用花 5 小时排查。

10. **怀疑环境问题之前先简化到最小测试用例**：如果一开始就用 `import baostock; bs.login(); bs.query_xxx(code)` 5 行代码测试，10 秒就能确认 Baostock 单线程工作正常。而不是在 ThreadPoolExecutor 的复杂环境中猜了两天。

11. **聚宽代码先在研究环境最小调用验证**：不要写完整策略再跑。先用 5 行代码调通 `get_price(panel=False)`，确认数据取得到，再往下写。两个 Panel 相关的 Bug（23、24）浪费了两轮回测。

12. **不要假设 API 返回格式——实测它**：我们假设了7个版本"columns=股票, index=日期"，直到环境验证才发现在聚宽当前版本中 `panel=False` 返回长格式 `['time','code','close']`。这不是文档能告诉你的——文档有多个版本，不同版本的聚宽行为不同。**以实测为准。**

13. **搜索文献→验证环境→制定方案→写代码**：这个四步流程应该成为任何新平台/新API开发的强制流程。在聚宽上违反这个流程的代价是8次报错×2天。
