# 数据下载优化方案

> 2026-07-11 | 绝对保障数据正确 + 最大化下载速度

---

## 现状分析

### 当前流程

```
遍历300只 → 每只查最新日期(SQL) → 需更新? → API下载 → sleep(0.15s) → 下一只
            失败重试3次(0.5s/1.0s退避) → 第二轮重试失败列表
```

### 耗时拆解（300只，缺5天数据）

| 环节                                | 耗时             | 占比 |
| ----------------------------------- | ---------------- | ---- |
| 300次SQL查询                        | ~15秒            | 9%   |
| sleep(0.15s) × 300                 | 45秒             | 28%  |
| 需更新股票的API下载（~200只×1.5s） | ~90秒            | 56%  |
| 重试                                | ~10秒            | 7%   |
| **总计**                      | **~160秒** |      |

---

## 优化方案

### 核心限制

AKShare 底层使用 V8 JS 引擎（libmini_racer），**不支持多线程**。实测 ThreadPoolExecutor 会触发 FATAL 崩溃。采用串行优化方案。

### 1. 批量日期查询

当前每只股票一次 SQL（300 次查询）。

```
改为: 一次查询返回所有股票的最新日期
SELECT code, MIN(date), MAX(date) FROM daily_kline GROUP BY code
→ 内存 dict 匹配，跳过已更新的
```

### 2. 去除无意义 sleep

原代码每只股票 `sleep(0.15)` = 45 秒纯等待。Sina/Eastmoney 免费接口无限流。

```
改为: 无 sleep
重试退避从 0.5s/1.0s 减为 0.3s/0.6s
```

### 3. 内存过滤已更新股票

批量查询后，`last_date >= today` 的股票直接在内存过滤，不进下载循环。

---

## 优化后流程

```
一次 SQL → {code: (first_date, last_date)} 内存 dict
    ↓
过滤: last_date >= today → 跳过(~100只)
      last_date < today → 下载列表(~200只)
    ↓
串行下载（无sleep，保留3次重试，退避0.3s/0.6s）
    ↓
第二轮串行重试失败列表（1.0s间隔）
    ↓
fix_pct_change() + verify_data_quality()
```

### 预估耗时

| 环节           | 优化前           | 优化后           |
| -------------- | ---------------- | ---------------- |
| 日期查询       | 15秒（300次SQL） | 1秒（1次SQL）    |
| 已更新检查     | 含在遍历中       | 0（内存过滤）    |
| 串行下载       | 90秒             | ~90秒（不变）    |
| sleep          | 45秒             | 0                |
| 重试           | 10秒             | ~8秒             |
| **总计** | **~160秒** | **~100秒** |
