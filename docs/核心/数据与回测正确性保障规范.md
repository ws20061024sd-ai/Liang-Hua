## 〇、总则

### 为什么需要这份文档

项目历史上出现过以下数据/回测问题，根源都是缺乏强制校验机制：

| 事故 | 根因 | 后果 | 发现延迟 |
|------|------|------|:--:|
| 财务数据仅 2/300 只 | Baostock 多线程登录 Bug | 因子引擎 35% 权重失效 | 数天 |
| 动量因子公式错误 | 数学推导错误，用了 `12月-1月` 而非 `(P[-21]-P[-252])/P[-252]` | 本地回测结果偏离 ~7pp | 数周 |
| ROE 全 NULL | Baostock 不提供 ROE，未验证 | 质量因子完全失效 | 数周 |
| macro.py NameError "已修复" | 审查记录标记已修复但代码未改 | Bug 继续潜伏 | 跨版本 |
| 本地 vs 聚宽结果差 35%→0.02% | 多因素叠加，无系统对比机制 | 基于错误结论做决策 | 数天 |

**这些事故不允许再发生。本文定义强制规则，每条规则可被自动化验证。**

### 核心原则

```
原则 1：数据完整性 > 策略开发速度
原则 2：聚宽回测 = 真理，本地回测 = 方向验证
原则 3：任何改动后必须跑校验脚本，通过才能继续
原则 4：校验失败 = 阻塞，不允许"先跳过以后修"
原则 5：代码和配置的修改必须在所有相关位置同步
```

## 一、数据正确性标准

### 1.1 日线数据（daily_kline）

| 指标 | 最低标准 | 目标标准 | 校验方式 |
|------|:--:|:--:|------|
| 股票覆盖数 | ≥ 280/300 | ≥ 295/300 | `COUNT(DISTINCT code) WHERE date = MAX(date)` |
| pct_change NULL 率 | 0% | 0% | `COUNT(*) WHERE date = MAX(date) AND pct_change IS NULL` |
| 数据起始日期 | ≤ 2019-06-01 | ≤ 2019-01-01 | `SELECT MIN(date) FROM daily_kline` |
| 数据新鲜度 | 当日或前一交易日 | 当日 | `SELECT MAX(date) FROM daily_kline` |
| 最新日股票数 | ≥ 280 | ≥ 295 | 同上 |

**校验脚本**：
```bash
python -c "
import sqlite3
conn = sqlite3.connect('data/stocks.db')
maxd = conn.execute('SELECT MAX(date) FROM daily_kline').fetchone()[0]
cnt = conn.execute('SELECT COUNT(DISTINCT code) FROM daily_kline WHERE date=?',(maxd,)).fetchone()[0]
nulls = conn.execute('SELECT COUNT(*) FROM daily_kline WHERE date=? AND pct_change IS NULL',(maxd,)).fetchone()[0]
print(f'日线: date={maxd} stocks={cnt}/300 nulls={nulls}')
# 阻塞条件
import sys
if cnt < 280: sys.exit('❌ 阻断: 股票数不足280')
if nulls > 0: sys.exit('❌ 阻断: pct_change有NULL')
print('✅ 日线数据通过')
"
```

### 1.2 财务数据 PE/PB（financial_data）

| 指标 | 最低标准 | 目标标准 | 校验方式 |
|------|:--:|:--:|------|
| PE 覆盖率（最新日） | ≥ 80% | ≥ 90% | PE 非 NULL 股票数 / 总股票数 |
| PB 覆盖率（最新日） | ≥ 90% | ≥ 95% | 同上 |
| 数据起始日期 | ≤ 2019-01-01 | ≤ 2019-01-01 | `SELECT MIN(date) FROM financial_data` |

**校验脚本**：
```bash
python -c "
import sqlite3
conn = sqlite3.connect('data/stocks.db')
maxd = conn.execute('SELECT MAX(date) FROM daily_kline').fetchone()[0]
# 财务数据取 ≤ maxd 的最新记录
df = conn.execute('''
    SELECT f.code, f.pe, f.pb FROM financial_data f
    WHERE f.date = (SELECT MAX(f2.date) FROM financial_data f2
                    WHERE f2.code = f.code AND f2.date <= ?)
''', (maxd,)).fetchall()
total = len(df)
pe_ok = sum(1 for _, pe, _ in df if pe is not None)
pb_ok = sum(1 for _, _, pb in df if pb is not None)
print(f'财务: PE={pe_ok}/{total} ({pe_ok/total*100:.0f}%) PB={pb_ok}/{total} ({pb_ok/total*100:.0f}%)')
import sys
if pe_ok < total * 0.80: sys.exit('❌ 阻断: PE覆盖率不足80%')
if pb_ok < total * 0.90: sys.exit('❌ 阻断: PB覆盖率不足90%')
print('✅ 财务数据通过')
"
```

### 1.3 ROE 数据（financial_roe）

| 指标 | 最低标准 | 目标标准 | 校验方式 |
|------|:--:|:--:|------|
| 最新季度覆盖率 | ≥ 85% | ≥ 95% | ROE 非 NULL 股票数 / 300 |
| 数据延迟 | ≤ 2 个季度 | ≤ 1 个季度 | 最新报告期距今 ≤ 6 个月 |
| 数据合理性 | ROE ∈ [-50%, 100%] | ROE ∈ [-30%, 60%] | MIN/MAX 检查 |

**⚠️ 财报滞后规则（2026-07-05 新增——血的教训）**：

ROE 数据使用**季度截止日**作为 date（如 `2020-06-30`），但半年报要到 8 月底才披露。回测在 7 月 1 日就能"看到"Q2 ROE → 严重未来数据泄露。

**强制规则**：ROE 查询必须滞后 120 天。

```
A股财报披露截止日：
  Q1 (3/31) → 4/30 前披露 → 实际可用 5月初   滞后 ~30天
  Q2 (6/30) → 8/31 前披露 → 实际可用 9月初   滞后 ~60天
  Q3 (9/30) → 10/31前披露 → 实际可用 11月初  滞后 ~30天
  Q4 (12/31) → 4/30前披露 → 实际可用 5月初   滞后 ~120天

保守处理：统一滞后 120 天。
查询逻辑：WHERE date <= (target_date - 120 days)
```

**代码位置**：
- `engine/factor_engine.py: _fetch_roe()` — 已实现 120 天滞后 ✅
- `backtest/local_factor_backtest.py: compute_factors()` — 已实现 120 天滞后 ✅

### 1.4 Point-in-Time (PIT) 数据原则

**核心概念**：每条数据有两个时间戳——**值日期**（数据代表的时间点）和**披露日期**（数据公开的时间点）。回测在 T 时刻只能使用"披露日期 ≤ T"的数据。

```
❌ 禁止：以"值日期"做数据切片
✅ 要求：以"披露日期"（或滞后的值日期）做数据切片

当前数据 PIT 状态：
  daily_kline (日线):    ✅ 当日行情数据，天然 PIT（前复权价格 = 当日已知）
  financial_data (PE/PB): ✅ Baostock 日频 PE/PB = 当日行情衍生，天然 PIT
  financial_roe (ROE):    ✅ 120天滞后 → 近似 PIT（2026-07-05 修复）
```

### 1.5 综合数据健康检查

**校验脚本**：
```bash
python -c "
import sqlite3
from datetime import datetime
conn = sqlite3.connect('data/stocks.db')
latest = conn.execute('SELECT MAX(date) FROM financial_roe').fetchone()[0]
cnt = conn.execute('SELECT COUNT(DISTINCT code) FROM financial_roe WHERE date=?',(latest,)).fetchone()[0]
minr, maxr = conn.execute('SELECT MIN(roe), MAX(roe) FROM financial_roe WHERE date=?',(latest,)).fetchone()
months_lag = (datetime.now() - datetime.strptime(latest, '%Y-%m-%d')).days / 30
print(f'ROE: 最新季度={latest} 覆盖={cnt}/300 范围=[{minr:.1f}%, {maxr:.1f}%] 延迟={months_lag:.0f}月')
import sys
if cnt < 255: sys.exit('❌ 阻断: ROE覆盖率不足85%')
if months_lag > 6: print('⚠️ 警告: ROE数据延迟超过2个季度')
if minr < -50 or maxr > 100: sys.exit('❌ 阻断: ROE数值异常')
print('✅ ROE数据通过')
"
```

## 二、回测正确性标准

### 2.1 本地回测与聚宽回测的角色定义

```
┌─────────────────────────────────────────────────────────────┐
│                      回测金字塔                               │
│                                                             │
│                    ┌─────────────┐                           │
│                    │  聚宽回测    │  ← 真理层：绝对收益判断    │
│                    │  (Truth)    │     参数锁定、上线决策     │
│                    └──────┬──────┘                           │
│                           │                                 │
│                    ┌──────▼──────┐                           │
│                    │  本地回测    │  ← 验证层：方向性判断      │
│                    │ (Direction) │     参数探索、因子筛选     │
│                    └──────┬──────┘                           │
│                           │                                 │
│                    ┌──────▼──────┐                           │
│                    │  因子引擎    │  ← 执行层：每日信号产出    │
│                    │ (Execution) │     与回测策略必须一致     │
│                    └─────────────┘                           │
│                                                             │
│  规则：上层验证通过 → 才能下沉到下层                           │
│  规则：下层代码必须与上层逻辑一致（公式、权重、数据）            │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 交易成本建模规范（2026-07-05 补充）

**成本少算是本地回测虚高的重要原因。必须严格建模。**

A股完整往返成本：

| 成本项 | 费率 | 收取方 | 建模方式 |
|------|:--:|------|------|
| 佣金 | 万1~万2.5 | 券商 | 双边，最低 5 元/笔 |
| 印花税 | 千1 (0.1%) | 国家 | **仅卖出** |
| 过户费 | 万0.1 | 中登 | 双边（金额小可忽略） |
| 滑点 | 0.1%~0.2% | 市场 | 沪深300 成分股假设 0.1% 单边 |
| 冲击成本 | 0~0.1% | 市场 | 小资金(<10万)可忽略 |

**往返总成本（与聚宽一致）**：
```python
# 聚宽配置:
#   open_commission = 0.0008/2 = 0.0004
#   close_commission = 0.0008/2 = 0.0004
#   close_tax = 0.0005
#   slippage = 0.001 (单边)
# 往返总成本 = 0.0008 + 0.0005 + 0.001×2 = 0.0033

COMMISSION = BACKTEST_COMMISSION + BACKTEST_TAX + 2 × BACKTEST_SLIPPAGE
           = 0.0008 + 0.0005 + 2 × 0.001
           = 0.0033  (0.33% per round-trip)
```

**小资金额外成本（¥10,000 本金）**：
```
每次交易约 5,000 元 × 2 只：
  买入佣金: max(5, 5000×0.00025) = 5元 = 0.10%
  卖出佣金: max(5, 5500×0.00025) = 5元 = 0.09%
  印花税: 5500 × 0.001 = 5.5元 = 0.10%
  合计: 0.29%（不含滑点）

→ 小资金实际成本可能比回测参数高 2-3 倍
→ 这是"回测好看，实盘亏钱"的常见原因
```

### 2.3 本地回测强制校验清单

**回测前**（跑 `local_factor_backtest.py` 之前）：

```
□ 数据校验通过（§1.4 综合检查无阻断项）
□ 因子公式与聚宽策略一致（对照 engine/factors.py ↔ 聚宽策略代码）
□ 权重与聚宽策略一致（对照 FACTOR_WEIGHTS）
□ 换手率因子使用成交量比率 v20/v60（非真实换手率%）
□ 涨停过滤已启用
□ 手续费/滑点参数与聚宽一致
```

**回测后**：

```
□ 交易月数 ≥ 60（5年以上，统计有意义）
□ 年化收益在合理范围（-30% ~ +50%，超出则可能是数据/代码Bug）
□ 至少与一个已知聚宽结果对标（目前基准: TOP_N=15 聚宽 10.05%）
□ 本地 vs 聚宽同 TOP_N 差距 ≤ 5pp（超过则需逐月排查）
```

### 2.4 本地 vs 聚宽对标规范

#### 对标时机
- 修改因子公式后 → 必须对标
- 修改权重后 → 必须对标
- 新增因子后 → 必须对标
- 修改数据源后 → 必须对标
- 首次运行新策略 → 必须对标

#### 对标方法

**Level 1（快速）—— TOP_N 一致性**：
```
在本地和聚宽各跑 TOP_N = [5, 10, 15, 20, 30]，对比：
  □ 收益最高的 TOP_N 一致
  □ 夏普最高的 TOP_N 一致
  □ 五组收益排序一致
通过 → 本地可做方向验证
失败 → 进入 Level 2
```

**Level 2（中等）—— 逐月持仓对比**：
```
取 3 个代表性月份（牛市/熊市/震荡市各一），对比：
  □ 前 20 持仓重合度 ≥ 60%
  □ 各因子排名相关系数 ≥ 0.7
通过 → 本地可做方向验证，差异可接受
失败 → 进入 Level 3
```

**Level 3（深度）—— 逐因子排查**：
```
逐因子对比本地 vs 聚宽的数值分布：
  □ 每个因子的 mean/p5/p95/std 差异 ≤ 30%
  □ Z-score 标准化后的得分分布一致
  □ 定位具体差异因子 → 修 Bug 或文档记录已知差异
```

### 2.4 已知差异声明

本地回测和聚宽回测之间**永远存在**以下差异，这些是数据源不同导致的，不可消除：

| 差异 | 原因 | 影响 |
|------|------|:--:|
| 底层价格数据 | AKShare vs 聚宽数据商 | 所有价格因子有微小差异 |
| ROE 计算口径 | 同花顺 vs 聚宽 | 质量因子排名可能不同 |
| PE/PB 时效性 | 日频(Baostock) vs 日频(聚宽) | 估值因子值不同 |
| 交易日历 | AKShare vs 聚宽 | 调仓日期可能差 1-2 天 |
| 停牌/涨跌停数据 | 本地无完整数据 | 本地可能选到不可交易的股票 |

**这些已知差异不影响本地回测的方向性判断能力。**

## 三、代码同步规则

### 3.1 因子公式——单源原则

```
❌ 禁止：在两个文件中各自实现因子计算
✅ 要求：所有因子计算必须从 engine/factors.py 导入

当前状态:
  engine/factors.py          ← 唯一定义处（已统一 ✅）
  engine/factor_engine.py    ← 导入 factors.py ✅
  backtest/local_factor_backtest.py ← 导入 factors.py ✅
  聚宽策略                     ← 手动同步（无法导入，需人工对照）
```

**聚宽策略同步检查清单**（每次修改 factors.py 后）：

```
□ momentum 公式一致：(P[-21] - P[-252]) / P[-252]
□ volatility 公式一致：60日收益率 std * sqrt(252)
□ reversal 公式一致：-(P[-1] - P[-6]) / P[-6]
□ turnover 公式一致：v20/v60 成交量比率取负
□ Z-score 标准化逻辑一致
□ 因子方向一致（正向/负向）
```

### 3.2 权重——单源原则

```
❌ 禁止：factor_engine 和 backtest 使用不同权重
✅ 要求：两处 FACTOR_WEIGHTS 必须完全相同

同步位置:
  engine/factor_engine.py      price_factors + value_weight + quality_weight
  backtest/local_factor_backtest.py  FACTOR_WEIGHTS dict
  聚宽策略                      FACTOR_WEIGHTS dict

检查命令: grep -A7 "FACTOR_WEIGHTS" 三处，确认数字一致
```

### 3.3 手续费/滑点——单源原则

```
❌ 禁止：回测文件 hardcode 手续费
✅ 要求：从 config/settings.py 读取

settings.py 配置项:
  BACKTEST_COMMISSION    (默认 0.0008)
  BACKTEST_SLIPPAGE      (默认 0.001)
  BACKTEST_TAX           (默认 0.0005)
```

## 四、操作规范

### 4.1 下载数据后必须做的事

```
每次执行 run.py（含数据下载）后:
  □ 跑 §1.4 综合数据健康检查
  □ 阻断项触发 → 不推送信号，改推"数据异常告警"
  □ 通过 → 正常推信号
```

### 4.2 修改因子/权重后必须做的事

```
1. 改 engine/factors.py
2. 同步改 backtest/local_factor_backtest.py（如果是权重）
3. 同步改 聚宽策略文件
4. 跑本地回测（5个TOP_N，~40秒）
5. 跑 factor_engine 验证（确认无ImportError/NameError）
6. 跑 pytest（26个测试，确认未破坏现有逻辑）
7. 如果数值变化很大（>5pp）→ 在聚宽跑一次验证
```

### 4.3 发布到服务器前必须做的事

```
□ 本地 pytest 全部通过（26/26）
□ 本地 run.py --no-update 无报错
□ 本地回测结果与上次对比，变化方向符合预期
□ 如果是策略变更 → 聚宽回测验证通过
□ git diff 确认没有意外修改
□ 更新 docs/更新日志.md
```

### 4.4 新数据源接入规范

```
接入任何新数据源前:
  1. 单只股票验证（取1只，看数据格式/字段/缺失率）
  2. 小批量验证（取10只，看成功率/耗时）
  3. 全量下载（300只）
  4. 校验覆盖率 ≥ 85%
  5. 抽查5只股票 vs 公开数据（新浪/东方财富网页）人工核对
  6. 文档记录：数据源、字段含义、已知限制
```

## 五、红线规则（绝对禁止）

### 🔴 数据红线

| # | 规则 | 违反后果 |
|:--:|------|------|
| D1 | **禁止**在数据校验未通过时推送信号 | 用户收到基于残缺数据的信号 |
| D2 | **禁止**跳过数据下载失败而不告警 | Bug 潜伏数天无人知 |
| D3 | **禁止**修改数据库结构后不更新校验脚本 | 校验脚本失效 |
| D4 | **禁止**手动修改数据库中的数据（如需修复→写脚本→记录） | 不可追溯、不可复现 |
| D5 | **禁止**在数据库路径/表名变更后不同步更新所有引用 | 生产崩溃 |

### 🔴 回测红线

| # | 规则 | 违反后果 |
|:--:|------|------|
| B1 | **禁止**用本地回测的绝对数值做上线决策（聚宽必须验证） | 实盘效果与回测严重偏离 |
| B2 | **禁止**回测代码和实盘代码使用不同的因子公式/权重 | 回测好看的策略实盘无效 |
| B3 | **禁止**对着测试集调参后不加声明地报告结果 | 过拟合，实盘必亏 |
| B4 | **禁止**回测结果不报告数据区间和交易月数 | 不同区间不可比 |
| B5 | **禁止**修改回测参数后不跑全量 TOP_N 对比（5个点） | 看不到参数对整体的影响 |
| B6 | **禁止**使用未滞后的财务数据做回测（财报值日期 ≠ 披露日期） | 未来数据泄露，收益虚高 3-8pp |
| B7 | **禁止**回测交易成本低于聚宽往返总成本（0.33%） | 成本低估，收益虚高 |
| B8 | **禁止**下载新数据源后不验证覆盖率就用于回测 | 残缺数据产生虚假信号 |

### 🔴 数据红线（补充）

| # | 规则 | 违反后果 |
|:--:|------|------|
| D6 | **禁止**在财报数据中使用"季度截止日"做查询切片（必须滞后 ≥ 120天） | 前视偏差 |
| D7 | **禁止**在回测中混用前复权和后复权价格 | 后复权隐含未来信息 |
| D8 | **禁止**在不确认 PIT 属性的情况下使用新数据源 | 不知不觉引入未来数据 |

### 🔴 代码红线

| # | 规则 | 违反后果 |
|:--:|------|------|
| C1 | **禁止**在 `except Exception` 块中使用 `pass`（必须至少 print 到 stderr） | 异常静默消失 |
| C2 | **禁止**在策略/因子文件中硬编码参数（必须在 settings.py 或文件头部常量区） | 参数散落，改了不知 |
| C3 | **禁止**修改了因子公式但不同步更新聚宽策略文件 | 本地和聚宽分叉 |
| C4 | **禁止**提交包含 token/key/密码的代码到 Git | 安全事故 |
